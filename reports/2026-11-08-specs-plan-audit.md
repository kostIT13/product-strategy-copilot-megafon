## Вывод о PostgreSQL и Docker

**Для выполнения ТЗ обязательны сохранение состояния, проверяемые основания и возобновление; конкретная серверная БД и контейнеры не обязательны.** В ТЗ нет требований PostgreSQL, Docker, SQLAlchemy, Alembic, многопользовательского backend, собственного HTTP-приложения или автономного runtime. При этом ТЗ не запрещает вспомогательную БД/контейнер: их наличие само по себе не нарушает формат проекта-папки. Нужны понятная установка, перечисленные зависимости и измеримая польза (§§1, 5, 8, 9, 13).

| Компонент | Что даёт текущей реализации | Нужен ли по ТЗ | Рекомендация аудита |
|---|---|---|---|
| Постоянное состояние, журнал и source revisions | Продолжение, provenance, проверка актуальности и история решений | Да, поведение обязательно | Сохранить независимо от технологии хранения |
| PostgreSQL | Транзакции, связи/FK, конкурентные операции, FTS; эти свойства уже проверялись smoke-сценариями | Нет требования серверной БД | Для одиночного IDE-сценария сделать необязательным расширением, если выбираем облегчённый основной путь; не объявлять такое переключение уже реализованным |
| Docker Compose | Воспроизводимо поднимает локальный PostgreSQL и его зависимости | Нет | Оставить способом установки dev/integration окружения, не обязательным шагом первого запуска |
| Dockerfile | Упаковка CLI и проверки окружения | Нет | Опциональная упаковка/CI; контейнер сам по себе не превращает приложение в автономный сервис |
| SQLAlchemy/Alembic | Репозитории и миграции PostgreSQL | Нет | Сохранить для PostgreSQL adapter, если он остаётся; не требовать от файлового сценария |
| FastMCP/CLI | Узкие инструменты среды над валидаторами/состоянием | Оценивается оправданная интеграция, оба одновременно не предписаны | Сохранить выбранный thin-adapter подход; агентный цикл ведёт IDE |

PostgreSQL может быть оправдан общим конкурентным хранилищем, несколькими процессами, большим корпусом или доказанным выигрышем запросов/поиска. Текущие проверки показывают техническую работоспособность, но в рассмотренных материалах нет сравнения пользовательской пользы PostgreSQL с файловым workflow на целевой задаче. Один лишь backup/FTS/набор миграций не доказывает преимущество для жюри.

Docker и PostgreSQL независимы: PostgreSQL можно запускать без Docker, а Docker можно использовать только для упаковки/CI без БД.

## Внутренние противоречия плана

1. Разделы 1/3 объявляют PostgreSQL источником истины полной системы, а раздел 7 по-прежнему говорит: «JSONL — единственный канонический реестр утверждений, источников и решений». Appendix A.1 одновременно называет каноническими state.json/JSONL/decision.md и рабочим хранилищем PG. Нужно выбрать канон для конкретного runtime и явно описать производные представления/миграцию.
2. Основной workflow и подробные контракты написаны вокруг psa + projects/<id>, а roadmap основной разработки — вокруг psa-main + PG. Это две реально существующие ветки поведения, а не доказанная взаимозаменяемость одного ядра. Не обещать feature parity или переносимость без проверки.
3. План обещает отсутствие зависимости основного IDE-сценария от собственного LLM API, но новая selection→strategy→approval цепочка требует сохранённого strategy_plan run API-инструмента. Read-only promise preflight уже принимает IDE-authored текст напрямую, но это ещё не весь IDE-native workflow.
4. Ближайшие работы углубляют транзакционные журналы обещаний, а инструкции/knowledge integration остаются на этапе 6. Требование проекта-папки с полезным агентом требует обратного приоритета: сначала реально доступный IDE-процесс и результаты.

## Рекомендуемая корректировка приоритетов

1. Зафиксировать один основной сдаваемый сценарий: открыть проект в поддерживаемой IDE, загрузить правила/knowledge, провести исследование, сохранить читаемые артефакты и продолжить после перерыва. Базовый запуск не должен требовать Docker/PostgreSQL, если выбирается облегчённая архитектура.
2. В ближайший этап перенести AGENTS.md, минимальные рабочие skills и тонкие проверенные IDE-адаптеры, навигацию knowledge/ и прямой приём структурированных артефактов от IDE-агента без нашего LLM-вызова.
3. Закрыть обязательные оставить/закрыть, полноту обеих стратегий, метрики/базу/срок/защитные сигналы, корректировку и пересмотр оснований. Не подменять их дополнительным approval registry.
4. Пройти новый разрешённый кейс, проверить stop/correct/resume в новом чате и второй среде, записать время/расходы и провести сопоставимый baseline. Отложенные приёмки остаются отложенными до отдельного продолжения.
5. Подготовить обязательные видео и описание. PG/Compose/расширенный поисковый backend оставить измеряемыми расширениями либо обосновать их обязательность ADR с реальным сценарием и стоимостью запуска.

Если сохраняем PostgreSQL как основной backend по прежнему выбору, это допустимо: тогда план должен честно включить его в prerequisites и подтвердить setup/backup/project transfer/IDE-native путь. Но это не требование жюри и не бесплатное усиление решения.

## Цена облегчения текущей архитектуры

Сделать PostgreSQL «опциональным» сейчас нельзя одной правкой env или удалением Compose: bootstrap и новые repository/service chains работают с PostgreSQL, используют JSONB/FKs/FTS и транзакционные guards. Нужен отдельный ограниченный этап: инвентаризация реально нужных функций, один файловый adapter/единый state contract, безопасные записи/блокировки/идемпотентность, перенос нужных проверок и round-trip данных без потери provenance. Файловая версия также должна корректно переживать сбой; она не освобождает от согласованности состояния. Существующий domain/application код и валидаторы можно использовать, но полная переносимость всех новых срезов заранее не объявляется.

Действующие данные/миграции/контейнеры не удалялись и не останавливались. Выбор нового default/backend и переписывание основного плана — отдельная реализация после этого аудита.
