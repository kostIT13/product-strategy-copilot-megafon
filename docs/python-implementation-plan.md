# Подробный план реализации Python-части

## 1. Назначение и границы

Документ уточняет Python-реализацию проекта из [`solution-plan.md`](solution-plan.md). Репозиторий — переносимый набор инструкций, шаблонов и локальных инструментов для среды с ИИ-агентом, а не самостоятельный веб-сервис. Python отвечает за надёжную работу с файлами и структурированными данными: создать рабочую папку, проверить артефакты, анализировать открытые/разрешённые таблицы и собрать журнал использования. Модель и агентная среда остаются сменными; бизнес-логика не должна зависеть от конкретного API модели.

Оценки ниже — инженерный план, а не обещание фактической длительности. Они предполагают одного разработчика, знакомого с Python, один демонстрационный сценарий, работу без закрытых данных и готовые доступы к выбранному агенту. Время на ожидание доступов, согласование кейса и подготовку исходных материалов не включено.

## 2. Целевой стек

| Слой | Выбор для первого среза | Для чего | Когда добавлять другое |
|---|---|---|---|
| Интерпретатор | Python 3.11+; в CI и на демонстрации закрепить конкретную поддерживаемую версию | Совместимая база для скриптов Windows/macOS/Linux | Поднять минимум только после проверки зависимостей и целевых сред |
| Окружение и зависимости | `uv`, `pyproject.toml`, `uv.lock` | Повторяемая установка и запуск, единый lock-файл | `pip` + venv — запасной путь, если uv недоступен в целевой среде |
| CLI | `argparse` из стандартной библиотеки для первых команд | Минимум зависимостей для `init`, `validate`, `analyze` | `typer` при заметном росте CLI и необходимости удобных help-команд |
| Модели данных | `dataclasses` + стандартные `json`, `csv`, `pathlib`, `datetime`, `decimal` | Контракты состояния, источников, утверждений, действий и журналов | `pydantic` при появлении сложной внешней конфигурации и полезных сообщений об ошибках |
| Проверка JSON | Стандартная библиотека и явные валидаторы; `jsonschema` как опциональная зависимость | Проверка `state.json`, записей журналов и версий схем | Включить JSON Schema, если схемы потребуются нескольким инструментам/языкам |
| Табличные данные | Стандартный `csv`; `pandas` и `openpyxl` как отдельный extra | CSV в базовом режиме; xlsx-анализ только по необходимости | `pyarrow`/Parquet — лишь при доказанной потребности в больших объёмах |
| Сетевые запросы | Не включать в обязательное ядро; разрешённый браузер/инструмент агента | Сбор веб-источников и соблюдение ограничений конкретной среды | `httpx` для явно разрешённых, повторяемых read-only запросов; без обхода доступа |
| Тестирование и качество кода | `pytest`, `ruff`, типы через `mypy` или `pyright` (выбрать один) | Быстрая проверка утилит и единый стиль | `hypothesis` для сложных инвариантов; не нужен для MVP |
| CI | GitHub Actions или эквивалент площадки репозитория | Проверка установки, линтера и тестов на поддерживаемых ОС/версиях | Не требовать CI для использования папки; он обслуживает разработку |
| Логи | `logging` из стандартной библиотеки, структурированный JSONL в папке проекта | Ошибки, длительность, исходы команд; без содержимого документов и секретов | Внешняя система наблюдаемости для автономного сервиса не входит в MVP |

На старте не нужны FastAPI, база данных, Redis, Celery, Docker, LangChain/LlamaIndex, векторное хранилище или обязательный SDK конкретного LLM-провайдера. Это сервисные компоненты, которые увеличат настройку, но не решают ключевую задачу переносимого файлового workflow. Установка по умолчанию должна быть небольшой; `pandas`/`openpyxl` вынести в extra `data`, тестовые инструменты — в `dev`.

## 3. Предлагаемая структура Python-кода

```text
pyproject.toml
uv.lock
src/
  product_strategy_agent/
    __init__.py
    cli.py                 # команды и коды возврата
    config.py              # безопасные настройки и пути
    models.py              # типы артефактов и перечисления статусов
    project_init.py        # создание проекта из шаблонов
    validation/
      artifacts.py         # state, ссылки, обязательные поля
      paths.py             # проверки путей и файлов
    storage/
      jsonl.py             # чтение/добавление событий с проверкой
      atomic_write.py      # безопасная запись через временный файл
    analysis/
      csv_summary.py       # профиль таблицы с явными ограничениями
    usage/
      report.py            # сводка usage.jsonl и оценок стоимости
templates/                  # исходные шаблоны создаваемого проекта
tests/
  unit/
  fixtures/
scripts/                    # только тонкие совместимые обёртки, если нужны
```

Не следует создавать слой абстракций «на будущее» для единственного backend. Внутренние функции получают явный путь проекта и возвращают результат/ошибки; они не читают произвольные глобальные пути и не выполняют найденные в материалах команды. Тексты инструкций агента и Python-код версионируются раздельно, но совместимые версии форматов состояния должны быть указаны.

## 4. Контракты данных

Минимальные объекты и правила:

1. **ProjectState** (`state.json`): `schema_version`, `project_id`, временная метка UTC, текущий этап, выполненные этапы, открытые вопросы, перечень ожидаемых артефактов и следующее действие. Состояние — индекс и checkpoint, не копия содержимого документов.
2. **Source** (`sources.csv` или JSONL): стабильный `source_id`, URI/путь, тип, дата доступа, владелец/автор если известен, область/страница/лист, статус проверки и ограничение источника.
3. **Claim** (`claims.jsonl`): `claim_id`, текст, тип сведений (`fact`, `interpretation`, `hypothesis`, `forecast`, `synthetic`), ссылки на источники, уверенность, статус и дата. Синтетические выводы не могут маркироваться фактом.
4. **Decision event** (`decision-log.jsonl`): событие добавляется, а не переписывает историю; содержит тип события, ссылку на решение, автора/инициатора, дату и краткое обоснование.
5. **Usage event** (`usage.jsonl`): инструмент/модель, режим/задача, время, длительность, токены если доступны, стоимость и валюта/источник цены если рассчитаны, число попыток и признак оценки. Не записывать prompt, документы, секреты или персональные данные.

Схема должна иметь версию. Валидатор выдаёт понятные ошибки с именем файла и полем; некорректная запись не должна молча теряться. JSONL обрабатывается построчно, чтобы одна испорченная запись указывалась отдельно. Все времена сохраняются в ISO 8601 UTC. Денежные значения — десятичные числа с указанием валюты; если тариф неизвестен, стоимость отмечается как `unknown`, а не как ноль.

## 5. Команды CLI и поведение

Минимальный интерфейс:

```text
psa init <project-dir> [--template demo]
psa validate <project-dir> [--strict]
psa analyze-csv <file.csv> [--output <path>]
psa usage-report <project-dir> [--format text|json]
psa version
```

- `init` создаёт папку без перезаписи существующих пользовательских файлов; при конфликте завершается с понятной ошибкой. Генерирует случайный/предсказуемо уникальный ID и стартовую контрольную точку.
- `validate` проверяет схему, ссылки на источники и артефакты, обязательные этапы и опасные/неожиданные пути. Стандартный режим сообщает предупреждения, `--strict` делает обязательные ошибки ненулевым кодом возврата.
- `analyze-csv` показывает размер, заголовки, типы по выборке, пропуски, дубликаты и базовые сводки. Команда не делает причинных выводов и фиксирует ограничения выборки/форматирования.
- `usage-report` суммирует только имеющиеся события; отсутствующие токены или цены явно показываются как неизвестные.
- Выводы команд имеют стабильные коды завершения и краткий текст для человека; машинный JSON доступен для интеграции с агентом.

Команды должны быть идемпотентны там, где это ожидаемо. Запись артефакта — атомарная (временный файл в той же папке, затем замена). Не использовать `pickle`, не исполнять скрипты из папок проекта, не следовать символическим ссылкам за пределы явно заданной рабочей папки без отдельного решения.

## 6. Этапы и оценка времени

Оценка в человеко-днях (ч/д) для одного разработчика; 1 ч/д = около 6 часов сфокусированной инженерной работы. Документация и ручная подготовка демонстрации включены там, где указаны. Прогноз для одного разработчика: **10–15 рабочих дней** на надёжное Python-ядро MVP, плюс **4–7 дней** на полную демонстрацию с агентными инструкциями, исследованием и материалами сдачи. При параллельной работе команды календарный срок может сократиться, но интеграция и оценка останутся последовательными.

| Этап | Работа | Результат / критерий выхода | Оценка |
|---|---|---|---:|
| 0. Уточнить контракты | Проверить перечень артефактов и статусов; выбрать совместимые форматы; зафиксировать Python minimum и целевые ОС | Короткая схема JSON/CSV, sample проекта и решение по поддерживаемой матрице | 0,5–1 ч/д |
| 1. Упаковка и каркас | `pyproject.toml`, `uv.lock`, src-layout, CLI entry point, группы зависимостей, README quick start | Чистое окружение воспроизводимо устанавливается; `psa --help` работает | 1–1,5 ч/д |
| 2. Модели и файловые операции | Модели, чтение/запись JSON/JSONL/CSV, даты и ошибки, атомарная запись | Чтение валидных файлов и точные ошибки для повреждённых записей | 1–2 ч/д |
| 3. Инициализация проекта | Шаблоны, генерация ID, защита от перезаписи и проверка допустимого пути | Новый проект создаётся из пустой папки с контрольной точкой | 1–1,5 ч/д |
| 4. Валидатор | Схемы состояния/claims/usage, проверки ссылок, статусов и обязательных артефактов | Демо-проект проходит; набор намеренно испорченных входов даёт полезные ошибки | 1,5–2,5 ч/д |
| 5. CSV-профилирование | Стандартный CSV; опциональный xlsx через `pandas`/`openpyxl`; отчёт о пропусках и ограничениях | Повторяемая сводка с описанием единиц/выборки; закрытые данные не нужны | 1–2 ч/д |
| 6. Usage и отчёт | Разбор событий, агрегация длительности/токенов/известных затрат | Итоги не выдают неизвестное за ноль и имеют происхождение тарифа | 0,5–1 ч/д |
| 7. Сквозная проверка и упаковка | Ручной проход нового проекта, пауза/возобновление, инструкции для Windows/macOS/Linux, CI если доступен | Новый пользователь запускает путь из README; ограничения и ошибки задокументированы | 2–3 ч/д |
| **Итого Python-ядро** |  |  | **8,5–13,5 ч/д** |

Заложить ещё **15–25% резерва** на несовместимость форматов таблиц, особенности целевой среды, исправление usability ошибок и получение демонстрационных материалов. В календаре 8,5–13,5 ч/д обычно означают примерно 2–3 недели для одного человека с учётом переключений. Весь продуктовый кейс: добавить **4–7 рабочих дней** на workflow и инструкции агента, сквозное исследование, рубрику оценки, скриншоты и видео до 10 минут. Срок официального брифа и доступов может сдвинуть календарную дату.

### Что в оценку не входит

- создание SaaS/API-сервиса и постоянной БД;
- подключение платного поиска/моделей и согласование контрактов/доступов;
- обработка конфиденциальных корпоративных данных;
- реальные интервью и их транскрибация;
- сложный OCR, извлечение из PDF со сложной вёрсткой, аудио/видео и мультимодальный анализ;
- векторный поиск, маршрутизация между моделями, субагентная оркестрация;
- формальная безопасность/правовая сертификация и длительная сравнительная оценка на большой выборке.

## 7. Что потребуется от команды

### Обязательное

- Python 3.11 или новее на компьютере разработчика и чистой среде демонстрации.
- Git; выбранный удалённый репозиторий и права на публикацию материалов.
- `uv` либо разрешённый в среде способ создать virtualenv и установить зависимости.
- Одна доступная среда ИИ-агента с чтением файлов и инструкциями проекта; список реально доступных средств поиска/моделей.
- Открытый или специально подготовленный демонстрационный кейс, набор исходных документов/таблиц/сайтов и критерии решения.
- Оценщик/владелец продукта, который проверит полезность стратегии, а не только корректность CLI.

### Опциональное

- `pandas` + `openpyxl` для повторяемого анализа Excel; пользователь может поставить `.[data]`.
- Аккаунт/API-ключ провайдера только если нужная агентная среда его действительно требует. Ключ хранится вне Git, например в переменной окружения, и никогда не включается в usage или лог.
- CI runner на Windows, macOS и Linux для подтверждения переносимости.
- Инструмент поиска или MCP-интеграция с read-only-доступом, если в выбранной среде штатного веб-поиска недостаточно.

Необходимы также решения владельца: режимы глубины работы, лимиты времени/стоимости, точность поддерживаемых форматов, политика хранения материалов, официальная задача и сроки сдачи. Пока они не определены, фиксировать их как конфигурационные предположения, а не вшивать в код.

## 8. Проверки качества при разработке

Проверки нужны как часть плана реализации и приёмки (не как заявление о уже выполненных проверках):

1. **Модели:** корректная запись/чтение; неизвестная версия схемы; некорректная дата; отсутствующие и лишние поля.
2. **JSONL:** одна повреждённая строка указывается с номером строки, соседние записи доступны; повторное добавление не меняет прежнюю историю.
3. **Init:** пустая папка, существующий непустой каталог, недопустимые символы, повторный запуск и конфликт ID.
4. **Ссылки:** отсутствующий source ID, битый относительный путь, URL без даты доступа, утверждение без типа или источника.
5. **CSV:** UTF-8/BOM, разделитель, пустой файл, кавычки, большие файлы, пропуски и смешанные типы; отчёт не трактует корреляцию как причинность.
6. **Usage:** известная цена, неизвестная цена, частичные токены, дубликат события и валюта.
7. **Пути и приватность:** операции остаются внутри проекта; `.env`, ключи и исходные чувствительные материалы игнорируются Git; логи не содержат строк ячеек и документов.
8. **Переносимость:** установка и запуск на целевых ОС; инструкции с нуля; работа без интернет-доступа после установки для локальных команд.
9. **Сквозной сценарий:** остановка после этапа, закрытие чата, продолжение из файлов и пересмотр решения после добавления нового источника.

## 9. Версии, зависимости и обслуживание

`pyproject.toml` содержит ограничения совместимости, а `uv.lock` фиксирует разрешённые версии для повторяемого окружения. Обновлять зависимости следует намеренно: изменить lock, прогнать проверки на целевых ОС, записать причину. Не использовать плавающую установку «последней версии» в демонстрационных инструкциях. Релизы форматов `state.json` сопровождаются номером схемы и при необходимости скриптом миграции; при отсутствии безопасной миграции валидатор требует ручного экспорта/исправления и делает резервную копию.

Зависимости сгруппировать:

```text
default: минимум или ноль runtime-зависимостей
data: pandas, openpyxl (только если выбран xlsx-анализ)
dev: pytest, ruff, выбранный type checker
```

Не добавлять прямой SDK LLM-провайдера, пока Python-команды сами не вызывают модель. Если появится такой вызов, сделать интерфейс провайдера узким, вести журнал расхода и таймаутов, предусмотреть отключённый/ручной режим и не отправлять закрытые файлы невыбранному пользователем сервису.

## 10. Риски и способы сократить объём

| Риск | План |
|---|---|
| Python-скрипты дублируют обязанности файлового агента | Оставить в коде проверяемые механические операции; исследование и формулирование стратегии — workflow агента |
| Зависимости усложняют запуск на чужом компьютере | Базовые команды строить на stdlib; аналитические библиотеки — optional extra |
| Разные Excel-форматы и локали | Ограничить заявленную поддержку, сохранять исходник неизменным и сообщать ограничения разбора |
| Слишком много функций до демонстрации | Сначала `init` + `validate` + usage и один CSV-профиль; MCP, OCR и модели отложить |
| Автоматическая проверка создаёт ложное чувство достоверности | Валидатор проверяет структуру и ссылки, а не истинность утверждений; это прямо указать в выводе |
| Стоимость модели выглядит точнее реальной | Сохранять тариф/дату и признак estimated; без телеметрии показывать неизвестное |
| Потеря решения при сбое записи | Атомарная запись, резервная копия перед миграцией, добавочные журналы событий |

## 11. Критерий готовности Python-слоя

Python-слой можно считать готовым для демо, когда на чистой целевой среде новый пользователь устанавливает инструменты по README, создаёт изолированную папку проекта, проходит проверку артефактов, получает воспроизводимый профиль открытого CSV, видит сводку фактического/оценочного расхода, останавливает и возобновляет сценарий по сохранённым файлам, а ошибки и ограничения сообщаются понятным языком. При этом ни обязательного платного API, ни закрытых данных, ни секретов в Git не требуется.
