# Стратегия Фабрики продуктов — полный план разработки ИИ-агента

> Markdown-версия приложенного документа «Стратегия Фабрики продуктов — полный план разработки ИИ-агента». Содержание сохранено без изменений; восстановлены только структуры (таблицы, списки, блоки кода), потерянные при конвертации текста.

Я бы подошёл к этому проекту не как к разработке очередного AI-чатбота, а как к созданию полноценной агентной системы для продуктовой аналитики и принятия стратегических решений.

Причём здесь есть важный нюанс: жюри оценивает не количество используемых LLM, фреймворков и субагентов, а то, насколько хорошо агент умеет исследовать проблему, проверять информацию, рассматривать альтернативы и выдавать обоснованные решения.

Моя рекомендация — сделать **Product Strategy Agent Workspace**: переносимую папку проекта, которую можно открыть в Cursor, Claude Code, Codex или другой AI IDE.

Внутри будут:

- **Главный агент** — руководитель исследования и принятия решений.
- **Специализированные субагенты** — исследователи рынка, аудиторы UX, аналитики данных и стратеги.
- **Набор Skills** — повторяемые методики выполнения задач.
- **База знаний** — методологии, источники, исследования и история решений.
- **Инструменты** — поиск в интернете, работа с документами, таблицами, сайтами, изображениями и данными.
- **Workflow** — управляемый процесс от постановки задачи до стратегии.
- **Persistence** — сохранение состояния, чтобы продолжить работу в новом чате.
- **CLI** — удобный запуск и управление агентом из терминала.
- **Система оценки** — проверка качества результатов, стоимости и времени.

Главная идея: не строить продукт, который генерирует стратегию, а построить систему, которая собирает доказательства, проверяет гипотезы и помогает человеку принять решение.

## 1. Это просто LangGraph + FastAPI?

Нет. И я бы не рекомендовал ограничиваться этой связкой.

LangGraph и FastAPI — это только два инфраструктурных компонента.

- LangGraph отвечает за управление состоянием и выполнением агентного процесса.
- FastAPI предоставляет HTTP API, если оно действительно нужно.
- Но ни один из них сам по себе не обеспечивает качественное исследование рынка, проверку гипотез, методологию продуктовой стратегии, работу с источниками и сохранение оснований решений.

Более того, FastAPI вообще не является обязательным компонентом для данного задания.

Я бы разделил систему на пять уровней:

```
1. Пользовательский уровень
   Cursor / Claude Code / Codex / CLI

2. Agent Orchestration
   LangGraph · Router · Supervisor · Subagents

3. Skills
   Research · JTBD · SWOT · UX · Pricing · GTM · Experimentation

4. Tools
   Web · PDF · Excel · SQL · Browser · MCP · Python

5. Knowledge & Persistence
   Markdown · SQLite · DuckDB · Evidence Store · Decision Log · Checkpoints
```

При этом результатом будет не просто ответ LLM, а структурированный набор артефактов:

1. Product Brief.
2. Research Plan.
3. Evidence Register.
4. Hypothesis Register.
5. Competitor Analysis.
6. Strategic Options.
7. Product Strategy.
8. Communication Strategy.
9. Experiment Plan.
10. Decision Record.

Это принципиально важно: каждый артефакт можно проверить, исправить, сохранить и использовать в последующих сессиях.

## 2. Рекомендуемый технологический стек

Я предлагаю стек, который достаточно серьёзный для демонстрации агентной архитектуры, но не превращает проект в микросервисную инфраструктуру на 20 компонентов.

**Моя рекомендация:** `Python + LangGraph + Pydantic + SQLite + DuckDB + MCP + CLI`

### 2.1. Основной стек

| Компонент | Технология | Назначение |
|---|---|---|
| Язык | Python 3.12+ | Основная логика |
| Package manager | uv | Зависимости и воспроизводимость |
| Agent Framework | LangGraph | Workflow и управление агентами |
| LLM Integration | LangChain / OpenAI SDK | Подключение моделей |
| Data Validation | Pydantic v2 | Структурированные данные |
| Model Routing | LiteLLM | Маршрутизация между моделями |
| Persistence | SQLite | Состояние, история, checkpoints |
| Аналитика | DuckDB | Анализ CSV, Excel, Parquet |
| Документы | PyMuPDF, python-docx, openpyxl | Чтение материалов |
| Web Research | Tavily / Brave Search | Поиск источников |
| Browser | Playwright | Анализ сайтов и интерфейсов |
| MCP | MCP Python SDK | Подключение внешних инструментов |
| CLI | Typer + Rich | Интерфейс управления |
| Observability | Langfuse | Трассировка и расходы |
| Testing | Pytest | Проверка компонентов |
| Evaluation | Promptfoo / DeepEval | Оценка качества |
| Export | Jinja2 + Markdown | Генерация отчётов |

### Почему именно LangGraph?

Здесь есть длинный процесс, который нельзя выполнять одним запросом к LLM:

1. Получить задачу.
2. Определить, чего не хватает.
3. Собрать материалы.
4. Сформировать исследовательские вопросы.
5. Провести исследование.
6. Проверить достоверность.
7. Сформировать альтернативы.
8. Сравнить альтернативы.
9. Получить подтверждение человека.
10. Разработать стратегии.
11. Проверить согласованность.
12. Сохранить результат.

LangGraph хорошо подходит для этого благодаря графу состояний, checkpointing и механизмам прерывания выполнения для получения решения от человека.

### Почему Pydantic?

Нам нельзя позволять агенту выдавать произвольную структуру, которую потом невозможно обработать.

Например, каждая гипотеза должна иметь определённую структуру:

```python
class Hypothesis(BaseModel):
    id: str
    statement: str
    category: Literal[
        "product",
        "market",
        "audience",
        "communication",
    ]
    evidence_for: list[str]
    evidence_against: list[str]
    confidence: float
    validation_method: str
    status: Literal[
        "unverified",
        "supported",
        "rejected",
        "inconclusive",
    ]
```

Аналогично создаются модели для источников, фактов, конкурентов, вариантов стратегии, экспериментов и решений.

Так мы получаем не просто набор Markdown-файлов, а систему с формализованными сущностями.

### 2.2. Какие модели использовать

Не нужно использовать самую дорогую модель для каждого действия.

Я бы сделал три уровня маршрутизации:

| Уровень | Задачи | Тип модели |
|---|---|---|
| Fast | Классификация, извлечение, маршрутизация | Быстрая и недорогая |
| Balanced | Анализ документов, конкурентов, гипотез | Средняя универсальная |
| Reasoning | Стратегические выводы, критика, выбор | Сильная reasoning-модель |

Например, можно использовать модели OpenAI, Anthropic или Google через единый адаптер.

Для маршрутизации можно взять LiteLLM. Он поддерживает маршрутизацию между разными развёртываниями, в том числе по стоимости, задержкам и загрузке.

**Принцип экономии:** дорогая модель вызывается тогда, когда результат действительно влияет на стратегическое решение.

Не нужно делать три дорогих вызова для определения типа загруженного PDF.

## 3. Архитектура агентной системы

Я бы не делал десять независимых агентов, которые бесконтрольно общаются друг с другом.

Оптимальнее использовать **Supervisor + специализированные агенты** с чёткими обязанностями.

### 3.1. Состав агентов

```
Product Strategy Supervisor
Главный агент · управление всем процессом
        │
        ▼
Распределение задач
        │
        ├── Research Agent        — Рынок, тренды, конкуренты, источники
        ├── Customer Agent        — Сегменты, JTBD, интервью, потребности
        ├── Data Analyst          — Метрики, SQL, Excel, статистика
        ├── UX Analyst            — Интерфейсы, сценарии, барьеры
        ├── Product Strategist    — Позиционирование, экономика, варианты
        ├── Communication Agent   — Сообщения, каналы, GTM
        └── Critic / Quality Gate — Проверка доказательств, противоречий,
                                    логики и полноты
```

### Обязанности каждого агента

#### 1. Supervisor Agent

Главный координатор. Он:

- Анализирует запрос.
- Определяет тип задачи.
- Выбирает необходимый workflow.
- Формирует план исследования.
- Решает, каких специалистов подключить.
- Проверяет промежуточные результаты.
- Запрашивает решение человека на контрольных точках.
- Следит за бюджетом и сроками.

#### 2. Research Agent

Проводит исследование рынка:

- Находит конкурентов.
- Изучает публичные тарифы и предложения.
- Сравнивает функциональность.
- Исследует тенденции.
- Сохраняет URL и дату получения каждого источника.
- Проверяет, насколько источники независимы.

#### 3. Customer Agent

Работает с аудиторией:

- Сегментация пользователей.
- JTBD.
- Customer Journey Map.
- Анализ интервью.
- Формирование гипотез о мотивации и барьерах.

Дополнительно — Synthetic Respondents: модельные собеседники для проверки вопросов и поиска возможных возражений. Их ответы обязательно маркируются как синтетические.

#### 4. Data Analyst

Анализирует таблицы и данные:

- Retention.
- Churn.
- Conversion.
- ARPU.
- LTV.
- CAC.
- Cohort Analysis.
- Funnel Analysis.
- A/B-тесты.

Расчёты выполняются Python/DuckDB, а не исключительно языковой моделью.

#### 5. UX Analyst

Анализирует:

- Публичные сайты.
- Скриншоты.
- Структуру страниц.
- Формы регистрации.
- Пользовательские сценарии.
- Проблемы понимания ценности.

**Важно:** агент не должен заявлять, что элемент интерфейса существует, если он не виден на скриншоте или не обнаружен в HTML.

#### 6. Product Strategist

Формирует продуктовые варианты:

- Развивать текущий продукт.
- Изменить позиционирование или аудиторию.
- Изменить продуктовую модель.
- Оставить всё как есть.
- Закрыть направление.

Оценивает затраты, потенциальные доходы, риски и компромиссы.

#### 7. Communication Agent

Разрабатывает коммуникационную стратегию:

- Сегменты аудитории.
- Потребительские барьеры.
- Value Proposition.
- Key Message.
- Proof Points.
- Каналы.
- Коммуникационные сценарии.
- План запуска.

#### 8. Critic Agent

Это очень важный компонент, который я бы обязательно реализовал.

Он проверяет работу остальных агентов:

- Есть ли подтверждение у каждого существенного факта?
- Не перепутана ли корреляция с причинностью?
- Не выданы ли предположения за факты?
- Не игнорируются ли негативные данные?
- Есть ли сильные аргументы против рекомендации?
- Соответствует ли рекламное обещание реальной функциональности?
- Можно ли воспроизвести расчёты?

Critic не должен просто переписывать стратегию. Его задача — находить ошибки и возвращать конкретные замечания на исправление.

## 4. Workflow — сердце проекта

Это, на мой взгляд, самая важная часть всей разработки.

Нужно показать, что агент не просто вызывает несколько LLM, а самостоятельно проходит управляемый исследовательский процесс.

### 4.1. Общая схема

| # | Этап | Действие | Результат |
|---|---|---|---|
| 01 | Intake | Product Brief |
| 02 | Clarification | Уточнённая постановка |
| 03 | Material Collection | Реестр материалов |
| 04 | Research Planning | План исследования |
| 05 | Parallel Research | Результаты исследований |
| 06 | Evidence Validation | Реестр доказательств |
| 07 | Hypothesis Analysis | Проверенные гипотезы |
| 08 | Strategic Options | Не менее 3 вариантов |
| 09 | Decision Gate | Выбор человека |
| 10 | Product Strategy | Продуктовая стратегия |
| 11 | Communication Strategy | Коммуникационная стратегия |
| 12 | Experiment Design | План проверки |
| 13 | Critic Review | Контроль качества |
| 14 | Finalization | Итоговый пакет документов |
| 15 | Monitoring | Контроль обязательств и пересмотр |

### 4.2. Как работает процесс на практике

Допустим, руководитель продукта вводит:

> У нас падает удержание пользователей цифрового сервиса. Нужно понять причины и определить, что делать дальше.

**Шаг 1. Intake**

Supervisor анализирует запрос.

Не нужно сразу задавать 20 вопросов.

Он определяет, что для начала необходимо знать:

- Что именно за сервис?
- Как определяется удержание?
- За какой период наблюдается падение?
- Какой сегмент пользователей затронут?

Если данных нет, он может начать исследование с явной фиксацией ограничений.

**Шаг 2. Research Planning**

Агент формирует вопросы, которые способны изменить решение:

- Ухудшился продукт или изменился состав аудитории?
- Есть ли проблемы с onboarding?
- Появились ли новые конкуренты?
- Изменились ли цена или условия?
- На каком этапе пользователь перестаёт пользоваться продуктом?

Для каждого вопроса назначаются нужные инструменты и источники.

**Шаг 3. Parallel Research**

Запускаются нужные субагенты.

Например:

- Research Agent исследует рынок и конкурентов.
- Data Analyst анализирует предоставленный CSV.
- UX Analyst исследует публичный интерфейс.
- Customer Agent анализирует имеющиеся интервью.

Здесь важно использовать параллельное выполнение только для независимых задач.

**Шаг 4. Evidence Validation**

Все результаты собираются в единую базу доказательств.

Пример:

| ID | Утверждение | Тип | Источник |
|---|---|---|---|
| E-001 | Retention снизился на 8 п.п. | Факт | CSV, расчёт |
| E-002 | Onboarding вызывает сложности | Гипотеза | UX-анализ |
| E-003 | Конкурент изменил тарифы | Факт | Публичный сайт |
| E-004 | Цена влияет на отток | Гипотеза | Пока не подтверждено |

Нельзя позволять агенту превращать гипотезу в факт после нескольких повторений в своих ответах.

**Шаг 5. Strategic Options**

Формируются минимум три варианта:

1. Оставить как есть.
2. Оптимизировать onboarding и активацию.
3. Пересмотреть ценность продукта, аудиторию или модель монетизации.
4. При наличии оснований — закрыть направление.

Для каждого варианта:

- Ожидаемый эффект.
- Необходимые ресурсы.
- Сроки.
- Риски.
- Аргументы за.
- Сильные аргументы против.
- Необходимые дополнительные данные.

**Шаг 6. Decision Gate**

Агент останавливается и показывает человеку варианты.

Человек выбирает направление, может изменить его или попросить дополнительное исследование.

**Шаг 7. Strategy Generation**

Разрабатываются согласованные продуктовая и коммуникационная стратегии.

**Шаг 8. Critic Review**

Critic проверяет документ.

Если находит проблемы, результат возвращается на нужный этап, а не генерируется полностью заново.

**Шаг 9. Finalization**

Сохраняются:

- Итоговая стратегия.
- Основания принятого решения.
- Отвергнутые альтернативы.
- Риски.
- Эксперименты.
- Ответственные.
- Сроки.
- Условия пересмотра.

**Шаг 10. Monitoring**

При появлении новых данных агент проверяет, какие выводы и решения они затрагивают.

Это позволит выполнить особенно интересную часть задания — продолжение работы после принятия решения.

### 4.3. Граф LangGraph

Пример того, как я бы организовал граф:

## 5. Структура GitHub-репозитория

### 5.1. Самое важное — разделение контекста

Я бы разделил знания на четыре независимые категории.

| Категория | Что содержит | Изменяется? |
|---|---|---|
| Instructions | Правила поведения агента | Редко |
| Knowledge | Методологии и экспертные знания | Периодически |
| Project Context | Материалы конкретного проекта | Постоянно |
| Run State | Текущий этап, checkpoints, прогресс | Во время работы |

Например, `knowledge/methodology/jobs_to_be_done.md` содержит постоянную методологию JTBD.

А `workspace/projects/demo/research/customer_segments.md` содержит выводы по конкретному проекту.

Их нельзя смешивать.

Особенно важно, чтобы старые выводы агента не превращались автоматически в новые факты.

## 6. Skills — повторяемые экспертные процедуры

Skills — одна из возможностей, которую я бы обязательно реализовал.

Вместо того чтобы помещать всю методологию в огромный системный промпт, мы создаём отдельные инструкции для каждого типа работы.

Например, `skills/market-research/SKILL.md`:

```markdown
---
name: market-research
description: >
  Conduct evidence-based market research,
  competitor analysis and market assessment.
---

# Market Research Skill

## Objective

Исследовать рынок и найти сведения,
которые способны повлиять на продуктовую стратегию.

## Workflow

1. Определи исследовательский вопрос.
2. Сформируй список проверяемых вопросов.
3. Определи необходимые источники.
4. Найди публичные источники.
5. Извлеки релевантные сведения.
6. Сохрани URL и дату получения.
7. Проверь достоверность и актуальность.
8. Найди противоречащие сведения.
9. Сформируй выводы.

## Rules

- Не выдумывать рыночные данные.
- Не считать рекламные заявления независимыми доказательствами.
- Разделять факты и гипотезы.
- Не использовать один источник для подтверждения
  всех существенных выводов.
- Указывать ограничения исследования.

## Output

- Market Overview
- Competitor Matrix
- Market Trends
- Evidence Register
- Research Gaps
- Strategic Implications
```

### Какие Skills реализовать

| Skill | Что делает |
|---|---|
| Intake | Превращает запрос в Product Brief |
| Market Research | Исследует рынок |
| Competitor Analysis | Сравнивает конкурентов |
| JTBD Research | Выявляет задачи пользователей |
| Interview Analysis | Анализирует реальные интервью |
| Synthetic Interview | Моделирует возможные реакции |
| UX Audit | Исследует пользовательский опыт |
| Data Analysis | Анализирует количественные данные |
| Hypothesis Testing | Проверяет гипотезы |
| Strategic Options | Формирует варианты решений |
| Product Strategy | Создаёт продуктовую стратегию |
| Communication Strategy | Создаёт коммуникационную стратегию |
| Experiment Design | Разрабатывает эксперименты |
| Decision Monitoring | Отслеживает принятые решения |

**Важный момент:** Skill — это не отдельный агент. Это инструкция и методика выполнения конкретной задачи, которую может использовать несколько агентов.

Например, Product Strategist и Supervisor могут использовать один и тот же Skill по оценке стратегических альтернатив.

## 7. База знаний и память между сессиями

Здесь можно получить серьёзное преимущество по сравнению с обычными AI-чатами.

Я бы сделал не просто RAG, а **Evidence-Centric Knowledge Base**.

То есть база знаний, в которой главным объектом является не текстовый документ, а проверяемое утверждение с происхождением.

### 7.1. Что сохранять

Предлагаю следующие сущности:

| Сущность | Содержание |
|---|---|
| Source | Исходный документ или сайт |
| Evidence | Конкретное подтверждаемое утверждение |
| Hypothesis | Непроверенная гипотеза |
| Finding | Результат исследования |
| Decision | Принятое решение |
| Strategy | Стратегия |
| Experiment | Эксперимент |
| Obligation | Обязательство |
| Observation | Новое наблюдение |

Пример цепочки:

```
Source S-001
Публичный отчёт / ссылка / дата
        |
        v
Evidence E-001
Проверяемое утверждение, извлечённое из источника
        |
        v
Hypothesis H-001
Интерпретация доказательства, требующая проверки
        |
        v
Decision D-001
Решение, основанное на доказательствах и оценке рисков
        |
        v
Experiment EX-001
Проверка того, оправдалось ли решение
```

Это позволит ответить на вопрос:

> «Почему мы решили развивать именно этот сегмент?»

Агент сможет восстановить всю цепочку оснований, а не просто пересказать прошлый диалог.

### 7.2. Какие технологии использовать

Я бы начал без тяжёлой векторной инфраструктуры.

| Технология | Назначение |
|---|---|
| Markdown | Читаемые материалы проекта |
| SQLite | Метаданные, решения, гипотезы |
| SQLite FTS5 | Полнотекстовый поиск |
| DuckDB | Аналитические таблицы |
| Embeddings | Семантический поиск |
| Vector index | Поиск похожих материалов при необходимости |

На первом этапе SQLite FTS5 + embeddings вполне достаточно.

Не стоит сразу поднимать Qdrant, PostgreSQL, Redis и отдельный векторный сервер, если нет подтверждённой необходимости.

### Механизм продолжения после перерыва

В конце каждого значимого этапа сохраняется состояние:

```json
{
  "project_id": "demo-retention",
  "run_id": "run-001",
  "current_stage": "strategic_options",
  "completed_stages": [
    "intake",
    "material_collection",
    "research_planning",
    "parallel_research",
    "evidence_validation"
  ],
  "pending_tasks": [
    "compare_strategic_options"
  ],
  "awaiting_human_decision": false,
  "last_checkpoint": "checkpoint-006",
  "budget_used_usd": 1.42
}
```

Пользователь запускает:

```bash
product-agent resume demo-retention
```

И агент продолжает работу с сохранённого этапа.

**Важно различать два механизма:**

- **Checkpoint** — восстановление незавершённого workflow.
- **Knowledge Base** — долговременное хранение результатов и оснований.

Они решают разные задачи.

## 8. MCP, CLI, Hooks и Routing

Это дополнительный уровень, который я бы реализовал, поскольку он демонстрирует не только использование нейросетей, но и грамотное проектирование агентной инфраструктуры.

### 8.1. MCP

Model Context Protocol позволит стандартизировать подключение инструментов.

Я бы создал собственный MCP Server, который предоставит агенту:

| MCP Tool | Назначение |
|---|---|
| search_sources | Поиск источников |
| read_document | Чтение документа |
| search_knowledge | Поиск по базе знаний |
| get_evidence | Получение доказательств |
| analyze_dataset | Анализ таблицы |
| get_project_state | Получение состояния |
| save_finding | Сохранение результата |
| create_decision | Создание записи решения |
| get_decision_history | История решений |
| export_strategy | Экспорт стратегии |

Можно использовать официальный MCP Python SDK. Он позволяет создавать MCP-серверы и клиентов, предоставлять tools, resources и prompts, поддерживает стандартные транспорты.

**Но есть важный нюанс:** не надо создавать MCP-инструмент для каждой Python-функции.

MCP нужен для внешнего подключения и переиспользования инструментов в разных AI IDE. Внутренние функции могут вызываться напрямую.

### 8.3. Hooks

Hooks — действия, автоматически запускаемые при определённых событиях.

Я бы сделал следующие:

| Hook | Когда запускается | Что делает |
|---|---|---|
| before_tool | Перед вызовом инструмента | Проверяет права и бюджет |
| after_tool | После вызова | Сохраняет результат и источник |
| after_research | После исследования | Проверяет наличие доказательств |
| before_decision | Перед рекомендацией | Проверяет альтернативы |
| after_checkpoint | После сохранения состояния | Записывает прогресс |
| before_export | Перед экспортом | Запускает контроль качества |

Например:

```python
async def after_tool(result, context):
    await source_registry.save(result)
    await budget_manager.update(
        context.run_id,
        result.cost
    )
    await audit_logger.record(
        event="tool_completed",
        tool=context.tool_name
    )
```

Это поможет обеспечить прозрачность, воспроизводимость и контроль расходов.

### 8.4. Routing

Маршрутизация должна работать на двух уровнях.

**Task Routing:**

Определяет, какой специалист нужен.

Пример:

```
Пользовательский запрос
       |
       v
Task Classifier
       |
       +---- Market Research
       |
       +---- Data Analysis
       |
       +---- UX Audit
       |
       +---- Product Strategy
       |
       +---- Full Workflow
```

**Model Routing:**

Определяет, какую модель использовать.

Пример:

```
Задача
  |
  v
Model Router
  |
  +---- Simple Task -> Fast Model
  |
  +---- Research -> Balanced Model
  |
  +---- Strategic Decision -> Reasoning Model
  |
  +---- Failure -> Fallback Model
```

У маршрутизатора должны быть измеряемые критерии: стоимость, время, качество, тип задачи.

Дополнительно можно сделать тестовый набор задач, на котором сравниваются разные модели. Не нужно полагаться только на мнение самого маршрутизатора о том, какая модель лучше.

## 9. Анализ документов, таблиц, сайтов и мультимодальность

Это обязательный блок, который нельзя оставлять на уровне обещаний.

Я бы сделал единую систему ingestion — загрузки и обработки материалов.

### 9.1. Поддерживаемые материалы

| Материал | Чем обрабатывать | Что извлекать |
|---|---|---|
| PDF / DOCX / TXT / Markdown | PyMuPDF, python-docx, python-magic | Текст, таблицы, заголовки, страницы и ссылки |
| XLSX / CSV / Parquet | Pandas, openpyxl, DuckDB | Анализ таблиц, метрик, временных рядов и когорт |
| Websites | Tavily, BeautifulSoup, Trafilatura, Playwright | Поиск и исследование публичных сайтов |
| Изображения и скриншоты | Vision-модель | Анализ видимых элементов, интерфейсов, схем и визуальных материалов |
| Аудио и видео | Whisper или другая модель транскрибации | Транскрибацию, временные метки, содержание и визуальные сцены |

### 9.2. Аналитический модуль

Особенно важно не позволять LLM самостоятельно считать сложные показатели.

Например, для анализа удержания:

```python
import duckdb

query = """
SELECT
    cohort_month,
    month_number,
    active_users,
    cohort_size,
    ROUND(
        active_users * 100.0 / cohort_size,
        2
    ) AS retention_pct
FROM retention_cohorts
ORDER BY cohort_month, month_number
"""

result = duckdb.sql(query).df()
```

Агент формирует запрос, запускает расчёт, получает результат и интерпретирует его.

При этом необходимо проверять:

- Определение метрики.
- Единицы измерения.
- Временные интервалы.
- Пропуски.
- Дубликаты.
- Размер выборки.
- Метод расчёта.
- Статистическую неопределённость.

Для причинно-следственных выводов одного сравнения до и после недостаточно.

## 10. Продуктовая и коммуникационная стратегии

Именно здесь должна проявиться экспертность всей системы.

Я бы не ограничивался генерацией двух красивых документов.

Нужно сделать единый **Strategy Engine**, в котором две стратегии связаны общими решениями и доказательствами.

### 10.1. Продуктовая стратегия

Итоговый документ должен включать:

1. Executive Summary.
2. Проблема и контекст.
3. Целевые сегменты.
4. Jobs To Be Done.
5. Потребности и барьеры.
6. Анализ альтернатив.
7. Конкурентная среда.
8. Ценностное предложение.
9. Продуктовое направление.
10. От чего сознательно отказываемся.
11. Продуктовая модель.
12. Экономика и ресурсы.
13. Риски.
14. Метрики успеха.
15. План реализации.

### 10.2. Коммуникационная стратегия

1. Целевые аудитории.
2. Контекст использования.
3. Барьеры понимания и выбора.
4. Позиционирование.
5. Value Proposition.
6. Key Message.
7. Подтверждения обещания.
8. Каналы коммуникации.
9. Tone of Voice.
10. Коммуникационные сценарии.
11. План запуска.
12. Метрики коммуникаций.

**Ключевой принцип:** коммуникационная стратегия не может обещать то, чего нет в продуктовой стратегии.

Например, если продукт не гарантирует экономию 30%, нельзя использовать такое обещание в рекламе без подтверждённого основания.

### 10.3. План экспериментов

Каждая рекомендация должна иметь способ проверки.

Пример:

| Показатель | Значение |
|---|---|
| Гипотеза | Новый onboarding увеличит активацию |
| Основная метрика | Activation Rate |
| Baseline | Текущее значение |
| Целевое изменение | +5 п.п. |
| Сравнение | Контрольная и тестовая группы |
| Срок | 4 недели |
| Guardrail | Retention, ошибки, жалобы |
| Условие успеха | Заранее установленный критерий |
| Условие остановки | Рост негативных последствий |

Числа здесь — пример оформления, а не утверждение о реальном эффекте.

Важно также предусмотреть минимально обнаруживаемый эффект, необходимый размер выборки и длительность эксперимента.

## 11. Critic и система контроля качества

Я бы сделал отдельную систему Quality Gates. Это один из наиболее важных элементов для получения высоких баллов за проработанность.

Агент не должен самостоятельно считать собственную стратегию правильной только потому, что красиво её сформулировал.

### 11.1. Проверки

| Проверка | Что контролируем |
|---|---|
| Source Validation | Существуют ли источники |
| Citation Coverage | Подтверждены ли важные утверждения |
| Evidence Consistency | Нет ли противоречий |
| Fact Separation | Отделены ли факты от гипотез |
| Alternative Coverage | Есть ли минимум 3 варианта |
| Counterargument Check | Есть ли сильные возражения |
| Strategy Alignment | Согласованы ли две стратегии |
| Promise Validation | Подтверждены ли коммуникационные обещания |
| Experiment Validation | Есть ли проверяемые критерии |
| Economic Validation | Учтены ли затраты и доходы |

Я бы ввёл числовую систему оценки, например:

```
STRATEGY QUALITY REPORT

Evidence Coverage:       92/100
Source Reliability:      85/100
Hypothesis Validation:   88/100
Strategic Alternatives:  100/100
Counterarguments:        90/100
Product Alignment:       95/100
Communication Alignment: 96/100
Experiment Quality:      91/100

Overall: 92/100
```

Это иллюстрация интерфейса, а не реальные измерения.

Не нужно выдавать средний балл LLM за объективную вероятность правильности стратегии. Критические проверки лучше реализовать программно, а субъективные оценки — калибровать на размеченном наборе задач.

Например, если нет ни одного подтверждённого источника для важного утверждения, система должна не просто снизить оценку, а заблокировать выдачу этого утверждения как факта.

## 12. Продолжение работы после принятия решения

Это дополнительная возможность, которая может особенно выделить проект.

Я бы реализовал отдельный модуль **Decision Monitoring**.

Предположим, руководитель выбрал вариант:

> Инвестировать в изменение onboarding, чтобы повысить активацию.

Агент сохраняет:

- Какое решение принято.
- Кто его принял.
- Почему выбрано это направление.
- Какие альтернативы отклонены.
- На каких доказательствах основано решение.
- Какие метрики должны измениться.
- Кто отвечает за выполнение.
- Когда нужно проверить результат.
- При каких условиях решение пересматривается.

Пример `decision_record.json`:

```json
{
  "decision_id": "D-001",
  "title": "Improve onboarding",
  "status": "approved",
  "owner": "Product Manager",
  "rationale": [
    "E-001",
    "E-004",
    "H-002"
  ],
  "success_metrics": {
    "activation_rate": {
      "baseline": 0.32,
      "target": 0.37
    }
  },
  "review_date": "2026-12-01",
  "reconsideration_triggers": [
    "Activation does not improve",
    "Retention decreases",
    "Implementation cost exceeds estimate"
  ]
}
```

Показатели здесь условные.

**Что делает агент при появлении новых данных?**

Например, через месяц пользователь загружает новый отчёт.

Агент:

1. Извлекает новые факты.
2. Сравнивает их с прежними доказательствами.
3. Находит связанные гипотезы и решения.
4. Определяет, какие основания устарели.
5. Оценивает, изменился ли вывод.
6. Формирует предложение о пересмотре.
7. Передаёт решение человеку.

**Очень важно:** агент не должен автоматически менять статус принятого решения или переписывать историю. Он предлагает пересмотр, а человек подтверждает изменение.

## 13. Безопасность и устойчивость

Здесь я бы не оставлял всё на уровне инструкции в system prompt.

Нужно реализовать несколько защитных механизмов.

| Риск | Решение |
|---|---|
| Prompt Injection в документах | Изолировать содержимое источников от системных инструкций |
| Вредоносные ссылки | Проверка URL и доменов |
| Утечка API-ключей | `.env`, `.gitignore`, секреты вне репозитория |
| Опасные команды | Allowlist инструментов |
| Несанкционированные действия | Human Approval |
| Повторное выполнение | Idempotency Keys |
| Ошибки API | Retry с exponential backoff |
| Потеря состояния | Checkpointing |
| Превышение бюджета | Budget Manager |
| Недоступность модели | Fallback Provider |

**Отдельно:** тексты сайтов, PDF и результаты инструментов нужно считать недоверенными данными, а не инструкциями агенту. Это принципиально для защиты от prompt injection.

Для CLI-команд и Python-кода из внешних источников я бы вообще не предусматривал автоматическое выполнение.

### Устойчивость workflow

Например, если агент успешно исследовал 15 сайтов, а на 16-м получил ошибку, он не должен начинать всё заново.

Он сохраняет:

- Уже обработанные URL.
- Результаты извлечения.
- Состояние исследования.
- Ошибку.
- Количество попыток.

При повторном запуске продолжает с проблемного элемента.

Для внешних действий используем idempotency keys, а для уже сохранённых результатов — проверку идентификаторов и контрольных сумм.

### Budget Manager

Пример конфигурации:

```yaml
budget:
  max_total_usd: 10.0
  max_agent_calls: 80
  max_retries: 2

  research:
    max_sources: 30
    max_depth: 2

  model_routing:
    fast: 0.50
    balanced: 0.30
    reasoning: 0.20

  approval:
    required_before_strategy: true
    required_before_paid_tools: true
```

Числа — стартовые ограничения для демонстрации, не прогноз реальной стоимости.

Я бы также добавил три режима:

- **economy** — минимальное число вызовов и ограниченный объём исследования.
- **balanced** — рекомендуемый режим.
- **deep_research** — расширенное исследование с дополнительными проверками.

Это позволит показать, что агент умеет балансировать качество и стоимость.

| Имплементация | Сквозной workflow, CLI, checkpoints, тестирование |
| Качество | Экономика, наблюдаемость, UX, воспроизводимость |

И ещё один совет: не пытайтесь впечатлить жюри количеством агентов. Гораздо сильнее будет показать, как один Supervisor самостоятельно решает, что нужно исследовать, какие инструменты вызвать, какие доказательства собрать и когда остановиться для получения решения человека.

## 23. С чего конкретно начать разработку

Я бы начал с трёх последовательных задач:

**Первое** — спроектировать контракт данных. Создать Pydantic-модели для Project, Brief, Source, Evidence, Hypothesis, StrategicOption, Decision и Experiment.

**Второе** — реализовать один полноценный workflow. Intake → Research → Evidence → Strategic Options → Human Approval → Strategy → Critic → Export.

**Третье** — только после этого добавлять специализированных агентов, Skills, MCP и мониторинг.

Так вы не получите набор несвязанных демо-компонентов, а будете постепенно развивать работающий продукт.

**Мой главный вывод:** проект должен быть не LangGraph + FastAPI, а Agent Workspace + Orchestration + Knowledge + Tools + Decision Intelligence.

FastAPI здесь опционален. LangGraph — оркестратор. Настоящая ценность — методология исследования, доказательная база, управляемое принятие решений и способность агента продолжать работу после того, как человек выбрал стратегию.
