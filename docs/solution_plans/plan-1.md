# Подробный план действий и инструментов

## 0. Как пользоваться документом

Этот документ превращает архитектурный замысел в исполнимый план работ. Он описывает, что делать, чем делать, как именно применять инструмент в этом проекте, какой результат сохранить и как понять, что шаг завершён. Это план будущей реализации: перечисленные команды и библиотеки пока не означают, что код уже написан или что команда должна установить всё из списка.

Объём документа намеренно большой: в плане около 600 строк. Оценки даны для одного разработчика, который знает основы Python и Git, работает примерно по шесть сфокусированных часов в день и уже имеет доступ к выбранной среде агента. Время на ожидание брифа, согласований, учётных записей и данных указано отдельно.

### Условные обозначения

- **Обязательно** — нужно для заявленного файлового MVP.
- **Рекомендуется** — снижает ручные ошибки или помогает повторяемости, но MVP может жить без этого.
- **Опционально** — добавлять только при конкретной потребности и успешной пробе.
- **Отложить** — не нужно для первого демонстрационного среза.
- **Выход** — файл, команда, решение или проверяемое состояние, которое должно появиться по результату работы.

### Три уровня состава

1. **Минимальный запуск:** инструкции Markdown, шаблоны Markdown/JSON/CSV, Python стандартной библиотеки и Git.
2. **Разработческий набор:** `uv`, Python 3.11+, `pytest`, `ruff`, выбранный статический анализатор типов.
3. **Дополнительный анализ:** `pandas` и `openpyxl` для Excel; браузерный поиск или read-only интеграция для источников; внешние модели только через выбранную среду и с разрешёнными данными.

Не ставить все опции заранее. После каждого этапа принимать решение по правилу: конкретная повторяемая задача → минимальный подходящий инструмент → проба на одном кейсе → решение оставить или удалить.

## 1. Каталог инструментов: что выбрать и зачем

### 1.1. Репозиторий, среда и разработка

| Инструмент | Статус | Для чего здесь | Как применять | Выход / когда не нужен |
|---|---|---|---|---|
| Git | Обязательно | История инструкций, схем, кода и демонстрационных артефактов | Небольшие коммиты по завершённым этапам; проверять `git status` перед фиксацией | История изменений; не хранить закрытые данные и ключи |
| GitHub или GitVerse | Обязательно для сдачи, иначе условно | Размещение переносимого репозитория и просмотр жюри | Выбрать площадку до настройки CI; дать только требуемый доступ | URL сдачи; не переносить туда внутренние данные |
| Python 3.11+ | Обязательно для локальных утилит | Валидатор, инициализация, анализ CSV и usage | Проверить версию в README и на чистой демонстрационной машине | CLI; если Python не нужен для выбранного объёма, не создавать фиктивную зависимость |
| `uv` | Рекомендуется | Создание окружения, разрешение зависимостей и блокировка версий | Хранить `pyproject.toml` и `uv.lock`; запускать через `uv run` | Воспроизводимое окружение; запасной вариант — `venv` и `pip` |
| `pyproject.toml` | Обязательно, если Python оформлен как пакет | Метаданные, команды, зависимости и настройки качества | Указать минимум Python, CLI entry point, extras `data`/`dev` | Единая конфигурация вместо нескольких разрозненных файлов |
| `uv.lock` | Рекомендуется | Фиксация версий, реально разрешённых для проекта | Обновлять осознанно и коммитить вместе с изменением зависимостей | Повторяемая установка; не редактировать вручную без необходимости |
| `.gitignore` | Обязательно | Исключение `.venv`, ключей, логов и рабочих данных | Проверить шаблоны до добавления демонстрационных файлов | Меньше риск утечки; ignore не заменяет проверку staged-файлов |
| `README.md` | Обязательно | Первый запуск, требования, пример и ограничения | Написать команды с нуля для чистого checkout | Проверяемый путь нового пользователя |
| IDE/агентная среда (Codex, Cursor или совместимая) | Обязательно для использования продукта | Читает правила, ведёт исследование, готовит анализ и стратегии | Выбрать одну основную среду для демо, затем проверить переносимые артефакты | Не связывать схемы данных с внутренним форматом одного вендора |
| GitHub Actions или CI площадки | Рекомендуется | Автоматически проверить сборку и качество кода | Запускать lint и тесты на push/PR; матрицу ОС держать небольшой | Раннее выявление несовместимости; не является runtime-зависимостью |
| Docker | Отложить | Изолированная серверная доставка | Не добавлять для файлового локального workflow | Понадобится только при отдельном сервисе/контейнерной среде |

### 1.2. Python-ядро

| Инструмент | Статус | Для чего здесь | Как применять | Выход / ограничение |
|---|---|---|---|---|
| `argparse` | Обязательно на первом срезе | Команды `init`, `validate`, `analyze-csv`, `usage-report` | Создать простые подкоманды и стабильные коды завершения | Без новой зависимости и с базовой справкой |
| `pathlib` | Обязательно | Кроссплатформенная работа с каталогами | Все пути строить относительно переданной папки проекта | Не строить пути конкатенацией строк |
| `json` | Обязательно | Чтение и запись `state.json` | Проверять типы/обязательные поля после разбора | JSON парсер не подтверждает бизнес-смысл данных |
| `csv` | Обязательно | Реестр источников и базовый анализ таблиц | Явно задавать кодировку, заголовки и диалект; сообщать о неоднозначности | Хорош для умеренного CSV без сложной аналитики |
| `jsonl` через `json` и файловые потоки | Обязательно | Append-only журналы claims, событий и использования | Читать построчно; номер испорченной строки включать в ошибку | Удобно продолжать большие журналы и сохранять историю |
| `dataclasses` | Рекомендуется | Внутренние типы `Source`, `Claim`, `UsageEvent`, `ProjectState` | Использовать для ясных полей и внутренних преобразований | Не добавлять библиотеку, если модели совсем простые |
| `enum` | Рекомендуется | Закрытый список статусов этапов и типов утверждений | Перечислить допустимые типы, сериализовать явное значение | Предотвращает случайные варианты вроде `donee` |
| `datetime` | Обязательно | Метки времени и даты доступа | Сохранять timezone-aware UTC в ISO 8601 | Не смешивать местное время и UTC |
| `decimal` | Рекомендуется | Суммы и стоимость API | Использовать строковое JSON-представление/оговорённую сериализацию | Не использовать двоичный `float` для точных денежных сумм |
| `logging` | Обязательно для CLI ошибок | Диагностика запуска и технические ошибки | Логировать этап и длительность без текста источников и ячеек | Не использовать лог как журнал продукта или решений |
| `tempfile` + `os.replace` | Рекомендуется | Атомарная запись важных файлов | Создать временный файл в целевом каталоге, завершить запись, заменить целевой | Уменьшает риск частично записанного state |
| `jsonschema` | Опционально | Внешняя проверяемая JSON-схема и понятные ошибки | Добавить после стабилизации версии формата | Не обязательно для одного локального валидатора |
| Pydantic | Опционально | Сложная конфигурация, преобразование входных данных | Использовать на границах, где нужны строгие типы/ошибки | Не превращать простые локальные JSON в слой моделей без выгоды |
| Typer | Опционально | Расширенный CLI | Заменить `argparse`, если команды, help и completion стали неудобны | Не использовать вместе с `argparse` без ясной причины |
| `pandas` | Опционально (`data`) | Большие/смешанные CSV, профилирование и группировки | Использовать для воспроизводимых расчётов, исходник оставить неизменным | Не нужен ради чтения маленького CSV |
| `openpyxl` | Опционально (`data`) | Чтение `.xlsx` с листами, ячейками и формулами | Зафиксировать обработку формул/форматирования и включить имя листа в источник | Не поддерживает макросы как исполняемое поведение; не запускать макросы |
| `pyarrow` | Отложить | Быстрые колоночные данные и Parquet | Рассматривать при больших корпусах и измеренном узком месте | Избыточен для демонстрационной таблицы |
| `httpx` | Опционально | Явные HTTP read-only запросы | Таймауты, ограниченные домены/URL, User-Agent при необходимости, фиксировать URL и дату | Не обходить логины, CAPTCHA, paywall или robots-ограничения |
| FastAPI | Отложить | HTTP API отдельного приложения | Только если требования изменятся в сторону постоянно работающего сервиса | Репозиторий по текущему кейсу не требует web backend |
| SQLite | Отложить | Локальные запросы по растущему объёму структурированных событий | Сначала измерить предел JSONL; добавить миграции и экспорт | Не вводить базу раньше реальной потребности |
| Векторная БД | Отложить | Семантический поиск по крупному корпусу | Сначала сравнить с полнотекстовым поиском и точностью ответов | Не нужна для малой папки проекта |
| LLM SDK | Условно | Прямой вызов модели из Python-кода | Добавлять только если инструмент сам должен вызывать API и выбран провайдер | В MVP модель вызывается агентной средой, ключи кода не нужны |

### 1.3. Проверки, оценка и демонстрация

| Инструмент | Статус | Для чего здесь | Как применять | Ограничение |
|---|---|---|---|---|
| `pytest` | Рекомендуется | Проверка парсеров, валидатора, init и расчётов | Тестировать отдельные функции и ошибки на маленьких фикстурах | Тесты не доказывают качество стратегии или достоверность исследования |
| `ruff` | Рекомендуется | Линтер и форматтер | Запустить lint/format check в локальной работе и CI | Согласовать конфиг один раз, не смешивать много форматтеров |
| `mypy` или `pyright` | Рекомендуется | Статическая проверка типов | Выбрать один, наращивать типизацию у границ файловых схем | Не блокировать MVP сложной строгой типизацией сторонних пакетов |
| `hypothesis` | Опционально | Генеративные проверки инвариантов | Добавить для путей, JSONL и неоднородных CSV, если обычных примеров мало | Расход времени оправдан только для важных сложных случаев |
| GitHub Actions | Рекомендуется | Повторяемые проверки перед публикацией | Установка, линтер, типы, unit checks на выбранной матрице | Секреты в CI не нужны, если нет интеграционных сервисов |
| Браузерный поиск среды агента | Условно, нужен для веб-исследования | Находить публичные источники, получать страницы и ссылки | Записывать URL, дату доступа, автора/организацию, краткую привязку | Возможности зависят от выбранного агента; источник всё равно проверяется человеком |
| MCP read-only connector | Опционально | Доступ к разрешённому источнику/инструменту без ручного импорта | Ограничить нужными операциями чтения; вносить интеграцию после ручного сценария | Не обязательный путь; настроить файловый fallback |
| Синтетический набор данных | Обязательно для безопасного демонстрационного анализа при отсутствии открытых данных | Проверить формат/процесс без корпоративных данных | Явно маркировать генерацию; числа не называть реальными | Не использовать как доказательство спроса или эффекта |
| CSV/JSONL редактор | Удобство | Просмотр и ручная проверка результатов | Любой текстовый редактор с подсветкой; сравнивать Git diff | Ручная правка схемных файлов должна проходить валидатор |
| PDF/видеозапись инструменты | Для сдачи | Подготовить описание, скриншоты и видео ≤10 минут | Снимать только безопасную демонстрационную среду | Не включать секреты, личные данные и запрещённые материалы |

## 2. Конкретное применение инструментов в этом проекте

### 2.1. Где живёт каждая часть

| Материал/логика | Формат или инструмент | Источник истины | Обновляется кем |
|---|---|---|---|
| Постоянные правила работы агента | `AGENTS.md` или файл инструкций среды | Короткая навигация + документы `agent/` | Разработчик проекта |
| Этапы процесса | Markdown workflow | Один канонический файл, ссылки из адаптеров | Владелец workflow |
| Методики и рубрики | Markdown | `knowledge/` и `evals/` | Ответственный за методику |
| Состояние кейса | JSON | `projects/<id>/state.json` | CLI/агент при переходе этапа, после проверки |
| Источники | CSV или JSONL | `projects/<id>/sources.*` | Агент добавляет, человек проверяет |
| Утверждения | JSONL + читаемая карта Markdown | claims JSONL является машинной записью | Агент предлагает, человек правит/подтверждает |
| Решение | Markdown + журнал событий | Текущий decision-файл и append-only log | Человек принимает, агент оформляет |
| План валидации | Markdown и при необходимости JSON | Артефакт кейса | Команда продукта |
| Использование модели/инструментов | JSONL | Usage-журнал с известностью/оценкой цены | Интеграция/человек/агент по доступной телеметрии |
| Инициализация проекта | Python CLI | Код и шаблоны | Разработчик |
| Проверка структуры и связей | Python validator | Валидатор и схемы | Разработчик задаёт правила, авторы исправляют файлы |
| Анализ табличных данных | Python скрипты / notebooks только при необходимости | Сохранённый скрипт, вход и отчёт | Аналитик/агент совместно |
| История версий | Git | Коммиты инструкций/кода; решения имеют свой журнал | Команда разработки |

### 2.2. Минимальный граф зависимостей

```text
Git + README
  └── Python + pyproject + uv (локальные утилиты)
       ├── init → шаблоны → новый проект
       ├── validate → модели/схема → файлы проекта
       ├── analyze-csv → CSV stdlib; extra data: pandas/openpyxl
       └── usage-report → usage.jsonl

Среда агента
  ├── инструкции → workflow → файлы артефактов
  ├── браузер/интеграции (если разрешено) → реестр источников
  └── человек → решение/план проверки

pytest + ruff + type checker → локальная проверка → CI (если настроен)
```

Не создавать циклическую зависимость, где валидатор вызывает агента, агент обязан использовать валидатор, а запуск без сети невозможен. Python CLI должен быть полезен локально и без доступа к модели.

## 3. Рабочие правила и команды

Все примеры — целевой интерфейс, который надо реализовать. Имена команд можно скорректировать при первом прототипе, но README, CLI и скрипты после этого должны совпадать.

### 3.1. Подготовка среды разработчика

```powershell
git clone <repository-url>
cd <repository-folder>
uv sync --all-groups
uv run psa --help
uv run pytest
uv run ruff check .
```

Если CLI ещё не реализован, в начале этапа команда запускает эквивалентный модуль разработки, а не копирует неподтверждённый пример в README. Для машины без uv документировать альтернативный путь через `python -m venv .venv`, активацию и `pip install -e ".[dev]"` только если такой путь поддерживается конфигурацией пакета.

### 3.2. Целевые команды продукта

```text
psa version
psa init projects/demo --template demo
psa validate projects/demo
psa validate projects/demo --strict
psa analyze-csv projects/demo/input/retention_sample.csv --output projects/demo/analysis/retention-profile.md
psa usage-report projects/demo --format text
psa usage-report projects/demo --format json
```

CLI должен показывать полный usage при ошибке аргумента, завершаться ненулевым кодом для ошибки ввода/схемы и не оставлять частично созданный проект. Текстовые сообщения — для пользователя; JSON-режим — стабильный контракт, если он заявлен.

### 3.3. Предлагаемые коды выхода

- `0` — команда успешно завершилась.
- `1` — внутренняя неожиданная ошибка; детали идут в stderr/log, без трассировки по умолчанию.
- `2` — неверные аргументы CLI.
- `3` — файл/папка отсутствует или недоступна.
- `4` — ошибка структуры/валидации данных.
- `5` — необязательная функция недоступна, например не установлен `.[data]`.

Коды фиксировать в документации и не менять без причины: агенту и CI проще разбирать результат стабильно.

## 4. План выполнения по фазам

## Фаза A. Решения до написания кода

### A1. Зафиксировать задачи и границы

1. Прочитать `specs/case.md` и выписать обязательные результаты.
2. Из обязательного выделить: бриф, реестр источников, доказательства, варианты, решение, проверку, состояние.
3. Сверить это с `docs/solution-plan.md`.
4. Разделить обязанности агента, Python-утилит и человека.
5. Записать, что Python не должен сам сочинять стратегию или оценивать истинность фактов.
6. Зафиксировать, что текущая версия — файловая папка, а не SaaS.
7. Уточнить целевые ОС: минимум компьютер разработки и чистая демонстрационная среда.
8. Уточнить, должен ли пользователь запускать Python сам или только агент через команду.
9. Если пользователь не запускает CLI напрямую, упростить команды и примеры для агента.
10. Определить безопасный публичный/синтетический сценарий.
11. Проверить, что синтетические значения будут маркироваться во всех артефактах.
12. Сформировать список внешних действий и оставить их read-only.
13. Записать, какие источники/домены допустимы в демо.
14. Отделить открытые вопросы от блокирующих решений.
15. Сохранить решения в `docs/architecture.md` или в этом плане до реализации.

**Инструменты:** Markdown, Git, среда агента для чтения репозитория. Python и сторонние пакеты на этом шаге не нужны.

**Выход:** список требований MVP, границы Python, целевые ОС, безопасный демо-набор, открытые решения.

**Оценка:** 0,5–1 день.

### A2. Выбрать базовую конфигурацию

4. Не давать интеграции запись/отправку сообщений для исследовательского кейса.

7. Проверить работу с недоступным коннектором: понятная ошибка и ручной fallback.
8. Не делать MCP обязательным для инициализации, валидации или продолжения кейса.
9. Подключать только после работающего ручного пути.

**Оценка фазы G:** 0,5–2 дня в зависимости от источников и выбранных интеграций; простое использование browser tool — часть агентного workflow, не Python-разработки.

## Фаза I. Workflow агента и контроль человеком

### I1. Этапы и артефакты

1. Сформулировать шаги workflow из `solution-plan.md`.

4. Указать, какие шаги могут быть автоматическими и обратимыми.
5. Указать, где нужно решение человека.
6. Ограничить уточняющие вопросы теми, что меняют выбор/следующий шаг.
7. Задать checkpoint после каждого завершённого этапа.
8. При неудаче сохранять неудачу, а не отмечать шаг выполненным.
9. Не повторять дорогой запрос без проверки наличия результата.
10. При смене источника перечислять выводы, которые он может затронуть.

### I2. Переносимость инструкций

1. Создать канонический workflow в Markdown.
2. Сделать короткий entrypoint-файл для основной IDE.
3. Не копировать всю инструкцию в несколько мест.
4. Указать fallback, если IDE не поддерживает skills/hooks/MCP.
5. Проверить, что Markdown-артефакты открываются без агента.
6. Проверить, что новый чат может возобновить задачу только по файлам.
7. Записать различия между средами, если команды или контекст отличаются.
8. Не заявлять универсальную совместимость без реального пробного запуска.

### I3. Субагенты и маршрутизация

1. Сначала получить базовый результат одного агента.
2. Подготовить контрольную задачу и рубрику.
3. Замерить точность, время, цену и человеческие исправления.
4. Сформулировать конкретный независимый подзадачный участок, например критика источников.
5. Сравнить последовательный проход с параллельной критикой.
6. Проверить дублирование, противоречия, объединение результатов.
7. Субагентам дать ограниченные входы и выходной формат.
8. Не давать им разрешения выше основного процесса.
9. Включать режим только если выигрыш измерен и превосходит стоимость координации.
10. Не добавлять маршрутизатор модели на основе одной демонстрации.

**Оценка фазы I:** 2–3 дня на workflow и переносимые инструкции; продвинутые orchestration-функции отдельно.
