# Проверка клиентских обещаний по capability registry

> Историческая документация старого контура. PostgreSQL/Alembic/Docker и psa-main удалены 10.11.2026; эти команды больше не являются инструкцией запуска. Текущий путь — [README](../README.md), состояние переноса — [R2](legacy-retirement.md).

`psa-main promise check` проверяет точные формулировки, подготовленные человеком или IDE-агентом, по доступным возможностям продукта и их фактическим основаниям. Это read-only preflight: он не вызывает модель, не требует отдельного LLM API-ключа, не создаёт run или решение и не зависит от `strategy_plan`. Пакет предназначен для следующего человеческого review, а не для публикации.

## Использование

Получить UUID и текущие связи через CLI:

```powershell
psa-main capability list PROJECT --json
psa-main claim list PROJECT --json
psa-main promise check PROJECT --input promises.json
```

Пример `promises.json` (подставить настоящие UUID из реестров):

```json
{
  "candidates": [
    {
      "key": "csv-pilot",
      "text": "Пилотным аккаунтам доступен CSV-экспорт в пределах дневного лимита.",
      "support": [
        {
          "capability_id": "CAPABILITY_UUID",
          "claim_ids": ["FACT_CLAIM_UUID"]
        }
      ]
    }
  ]
}
```

Нельзя подменять это обещанием «мгновенный безлимитный экспорт всех форматов», если источник описывает только пилотный CSV с ограничениями. Одинаковые ID и найденная цитата сами по себе не доказывают соответствие текста: человек проверяет смысл, аудиторию, форматы, сроки, условия и ограничения по содержимому review packet.

Exit code CLI: `0` — структура допускает человеческое review, `3` — есть blockers (stdout остаётся JSON), `2` — некорректный запрос/проект или файл. Main FastMCP открывает `psa_main_check_promises(project_key, request)` с тем же payload; business blockers возвращаются как данные, а не ошибка инструмента. Main inventory — 19 tools. Инструмент не пишет файлы и не делает внешних запросов.

## Программные проверки

- Каждая указанная capability существует в этом проекте и имеет статус `available`; `planned/unavailable` не подтверждают обещание текущей доступности.
- Каждый выбранный claim связан с соответствующей capability, принадлежит проекту, имеет `claim_type=fact`, `status=active` и хотя бы одну ссылку на источник. Все выбранные claims и все их citations должны пройти проверку: одного удачного основания недостаточно, чтобы скрыть плохое.
- Источник находится в этом проекте, имеет статус `extracted`, указанная revision остаётся последней, SHA-256 полного извлечённого текста совпадает и точная непустая цитата присутствует в нём.
- Locator citation должен совпадать с поддержанным locator сохранённой revision. Для более узкого fragment locator пока нет индекса, поэтому он блокируется как `locator_not_verified`; наличие цитаты где-то в документе не подтверждает произвольную страницу/ячейку.

Отдельный `PostgresPromiseEvidenceReader` читает только запрошенные capability/claim IDs и их evidence в одной транзакции `REPEATABLE READ, READ ONLY`. Поэтому preflight не смешивает разные версии при конкурентном изменении. Он не блокирует последующие изменения: результат относится к снимку чтения и не служит долговечным разрешением на действие.

## Результат и ограничения

`structural_status` равен `blocked` или `eligible_for_human_review`. В ответе есть исходные формулировки, состояния capabilities, тексты/типы claims, их fingerprints, цитаты, source hashes/revisions/locator, происхождение и ограничения источников, blockers и вопросы для review. Полный текст источника не возвращается. `review_hash` связывает пакет с формулировками и рассмотренными основаниями; при их изменении нужно повторить check. Это hash целостности, не подпись и не approval token.

Даже при корректной структуре всегда остаются:

```json
{
  "requires_human_review": true,
  "semantic_alignment_verified": false,
  "source_truthfulness_verified": false,
  "customer_promises_approved": false,
  "publication_approved": false,
  "workflow_approval_granted": false,
  "durable_approval": false
}
```

Активный fact — запись в реестре, а не доказательство истинности самого источника. Человек должен проверить происхождение, надёжность, ограничения, синтетическое происхождение и противоречия. Инструмент не проверяет все неуказанные источники и не извлекает обещания автоматически из произвольного текста стратегии. Автор запроса явно перечисляет формулировки и основания. [Внутреннее утверждение стратегии](strategy-approval.md) также не утверждает клиентские обещания; его экспорт не меняется этим preflight.

Ограничения запроса: 1–10 уникальных candidate keys, до 2000 символов на формулировку, 1–3 уникальные capabilities на candidate, 1–6 уникальных claim IDs на capability. CLI input — до 64000 байт; один snapshot — до 200 evidence references; проверка полного текста — до 200000 символов на source revision. Больший источник получает blocker `source_exceeds_check_limit`, без проверки только префикса. Review packet ограничен 128000 символов: превышение отклоняется с просьбой разбить запрос, не обрезается молча.

Следующий срез — явное человеческое решение по конкретным формулировкам с повторной транзакционной проверкой реестра перед сохранением; затем привязка к артефактам стратегии. Публикация пока не реализована. Для read-only среза новая Alembic migration не нужна: используется текущая схема `0017_strategy_approvals`.

## Проверка

```powershell
python -m unittest discover -s tests
python scripts/smoke_promises.py
```

Smoke создаёт синтетические проекты в development-БД, проверяет CLI/реальный stdio, JSON discovery UUID, блокировку planned и stale, отсутствие бизнес-записей от проверки, проектную изоляцию и согласованность снимка при конкурентном commit. Сам preflight работает с READ ONLY; подготовка/отрицательные пробы smoke меняют только его синтетические данные. Вызовов LLM нет.
